# Security Policy

CHOps holds ClickHouse&reg; credentials, issues session tokens, and executes SQL on
your behalf. We take reports about it seriously.

## Reporting a vulnerability

**Do not open a public issue.**

Report privately through GitHub's
[Report a vulnerability](https://github.com/Quantrail-Data/CH-Ops/security/advisories/new)
form, or email **chops@quantrail-data.com**.

Please include:

- The CHOps version and how it was deployed (binary, Docker, source)
- What an attacker can do, and what access they need to start
- Steps to reproduce, ideally with a minimal proof of concept
- Anything you think we would get wrong about the impact

## What happens next

| Stage | Target |
|---|---|
| We acknowledge your report | 3 working days |
| We confirm or dispute the finding, with reasoning | 10 working days |
| Fix released for a confirmed critical or high finding | 30 days |
| Public advisory published | With the fix, or sooner if already exploited |

If we are going to miss one of these, we will tell you rather than go quiet.

## Disclosure

We ask for 90 days before public disclosure, or until a fix ships, whichever
comes first. If we cannot fix something in that window we will say so and agree a
date with you rather than ask for open-ended silence.

You will be credited in the advisory unless you would rather not be.

We do not currently run a paid bug bounty.

## Scope

**In scope:** the code in this repository, and the binaries and container images
published from it.

**Out of scope:**

- Vulnerabilities in ClickHouse&reg; itself. Report those to ClickHouse, Inc.
- Vulnerabilities in third-party dependencies, unless CHOps uses them in a way
  that makes the impact materially worse. Dependabot covers routine updates.
- Findings that require an attacker to already hold `superadmin` credentials, or
  physical access to the host filesystem where `data/chops.db` and
  `data/crypto.salt` live.
- Missing hardening headers or rate limits with no demonstrated impact. Tell us
  anyway as a normal issue; we would like to know, it just is not an advisory.
- Reports generated by a scanner with no analysis attached.

## Deployment notes that are not vulnerabilities

These are documented behaviours. They are worth knowing, and they are not
findings:

- `ENCRYPTION_SECRET` derives the key that encrypts stored credentials. It
  cannot be rotated: a new value makes every stored credential unreadable.
- Rate limiting keys on `req.ip`. Behind a reverse proxy you must set
  `TRUST_PROXY` to the number of proxies in front of CHOps, or every client
  shares one bucket. We do not trust `X-Forwarded-For` by default because a
  spoofed header would otherwise defeat the limiter entirely.
- CHOps expects to run on a trusted network or behind your own authenticating
  proxy. It is an administration console for a database.

## Supported versions

| Release | Security fixes |
|---|---|
| Latest | Yes |
| Previous minor | Yes, for 90 days after the following minor ships |
| Older | No |

Report against a supported release where you can. If you can only reproduce it
on an older build, tell us anyway and we will work out whether it still affects
a supported one.

This covers the community edition. If you hold a commercial licence or CHOps
Pro, your agreement governs support and it takes precedence over this table.
